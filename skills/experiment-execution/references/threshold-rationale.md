# Threshold Rationale

Use this page whenever a research goal, experiment, or campaign decision introduces a number that will change a pass/fail, continue/stop, prioritization, or resource decision. Do not invent a threshold to make a goal look concrete. A number without a defensible source or derivation is not a gate.

## Gate register

| Gate | Current rule | Basis and interpretation |
| --- | --- | --- |
| Pilot/screening run count | Exactly one run per condition (one seed, one replicate ID, or one deterministic run). | The user-supplied AIAgent research rules explicitly require one run per exploratory condition. This is a local compute/anti-seed-shopping policy, not a field-wide statistical recommendation; pilot outcomes are exploratory only. If the owner changes that policy, update the gate and this rationale together before applying a different count. |
| Confirmatory stochastic count | One seed/replicate is allowed by default; further repeats are optional unless the benchmark or statistical claim requires them. | No universal seed count is prescribed by ML reproducibility guidance. Repeats used for inference or uncertainty need a predeclared count grounded in the estimand, effect/precision target, variance evidence, and dependence assumptions. Two or more observations are mathematically needed only if estimating a sample variance; that is not a requirement for every experiment and does not guarantee adequate power. |
| Late seed change to raise score | Optional optimization step, never an experimental requirement. | Treat changing seeds after observing scores as selection/optimization. Preserve all tried outcomes and disclose the selection rule. A selected high score is not an unbiased estimate or robustness result; claim-bearing reports must use the benchmark's official aggregation/selection protocol or explicitly study seed selection. Colas et al. discuss the risk of averaging best-performing runs. |
| Numeric goal or decision threshold | Every numerical pass/fail, continue/stop, success, or prioritization threshold must be listed in `decision_thresholds` with a source class, reference, exact locator, applicability, and derivation. | Use the exact official benchmark protocol, an applicable field standard, a peer-reviewed source, a predeclared statistical design, independent local empirical evidence suitable for that decision, an approved resource constraint, repository policy, or transparent mathematical derivation. A citation must support the value and match the metric, population, task, and decision. Do not tune a success threshold after viewing the current campaign's outcomes; a pilot may inform variance or resource estimates but does not automatically establish a meaningful success target. If no source supports the value, leave the goal qualitative or mark the decision blocked while gathering evidence; do not substitute an arbitrary value. |
| Threshold register | `decision_thresholds` may be empty only when no numeric decision thresholds are planned. | Structural completeness check, not a requirement to invent thresholds. Preflight checks each registered item has a value, operator, unit, basis type, reference, locator, applicability, and derivation. A human must still cross-check the protocol and goal documents because free prose can contain an unregistered threshold. |
| Benchmark unit count | Every required official scope is non-empty and executed count/population must match its official manifest exactly. | This is benchmark-defined, not a generic fixed sample-size threshold. Cite the official benchmark version, task list/split, loader/evaluator, and count in the campaign. A locally convenient subset is not an alternate threshold. If the official protocol defines a legitimate empty scope, it is not an evaluable campaign scope and needs explicit protocol review rather than silently weakening the gate. |
| Scope, condition, and run arrays | At least one of each required object. IDs/required strings must be non-empty. | Schema well-formedness invariants: an empty campaign or empty identifier cannot name an executable protocol, condition, run, or scope. These values are not empirical cutoffs and must not be described as evidence-based sample-size requirements. |
| Resource estimates | Runtime, memory, and storage estimates must be finite and greater than zero. | Campaign-contract validity and physical units: zero/negative/non-finite values are not usable estimates. Their magnitudes must be estimated from documented full-scope evidence (comparable run, benchmark throughput, or an explicit calculation); the positivity check does not validate estimate accuracy. |
| Hardware inventory | CPU count, memory, accelerator count, and reported per-device memory must be positive integers/bytes when present. | Structural validity for observed inventory. A CPU-only run uses an empty accelerator list. This is not a minimum hardware recommendation. |
| Runtime/timestamp consistency | Difference must be within the sum of the two timestamps' half-tick resolutions plus floating-point representation error. | Derived measurement bound, not a chosen seconds/percentage tolerance. Timestamps must be rounded to their displayed precision; the audit derives each resolution from the serialized ISO-8601 fraction (whole-second timestamps have one-second resolution). Preserve unrounded `runtime_seconds`. If clock steps or different clock sources make reconciliation invalid, record the source and flag the discrepancy for review; do not inflate a tolerance to force a pass. |
| Commit and artifact hashes | Accept full Git SHA-1/SHA-256 object IDs (40/64 hexadecimal characters); SHA-256 file digests are 64 hex characters. | Technical format requirements from Git's object-name documentation and NIST FIPS 180-4 digest definition, not empirical thresholds. |

## Sources

- Pineau et al., *Improving Reproducibility in Machine Learning Research* (JMLR 22, 2021), [paper](https://jmlr.org/papers/v22/20-303.html): describes the NeurIPS reproducibility checklist and reporting practices; it does not prescribe a universal seed count.
- NeurIPS, [Paper Checklist](https://neurips.cc/Conferences/2021/PaperInformation/PaperChecklist): asks for reproducibility details, error bars across repeated experiments/seeds, and compute reporting; it is a reporting checklist, not a universal sample-size formula.
- Colas, Sigaud & Oudeyer, *How Many Random Seeds? Statistical Power Analysis in Deep Reinforcement Learning Experiments* (2018), [paper](https://arxiv.org/abs/1806.08295): shows seed counts depend on statistical power and warns that small seed counts or reporting the best runs can mislead. Its RL examples are not a universal numeric rule for every field.
- Gundersen, Helmert & Hoos, *Improving Reproducibility in AI Research: Four Mechanisms Adopted by JAIR* (JAIR 81, 2024), [paper](https://doi.org/10.1613/jair.1.16905): checklist includes run counts and measures of variation/distributional information without asserting one seed count for every experiment.
- Git, [hash-function transition documentation](https://git-scm.com/docs/hash-function-transition.html): specifies 40-hex SHA-1 and 64-hex SHA-256 object names.
- NIST, [FIPS 180-4 Secure Hash Standard](https://csrc.nist.gov/pubs/fips/180-4/upd1/final): defines SHA-256 as a 256-bit digest, corresponding to 64 hexadecimal characters.

## Change control

When a numeric goal or gate changes, update this register, the implementing schema/script, user-facing instructions, fixtures, and changelog together. Record the source class and specific locator, show how it supports this exact decision, and explain whether the value is a necessary floor or an adequate target. Do not confuse thresholds for scientific outcomes with resource estimates, file-format bounds, or structural validation invariants. Never imply that a necessary floor alone proves power, robustness, or scientific validity.
